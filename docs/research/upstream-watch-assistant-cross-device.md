## Platform boundaries

**Eligibility, selection, hardware dispatch and automatic listening are four separate states.** AndroidX explicitly permits assistant qualification through **either** a `VoiceInteractionService` **or** an `ACTION_ASSIST` handler ([RoleManagerCompat](https://developer.android.com/reference/androidx/core/role/RoleManagerCompat#ROLE_ASSISTANT)). An activity assistant is valid; a dummy service is not necessary merely to qualify. A real voice-interaction stack adds a distinct session UI/lifecycle. Android keeps the selected [VoiceInteractionService](https://developer.android.com/reference/android/service/voice/VoiceInteractionService) running; this does not mean its microphone must run. Keep the service lightweight and recording explicitly invocation-bound. Do not confuse a recognition-service metadata requirement of the service route with a requirement for every activity assistant.

AOSP's inspected [roles.xml](https://android.googlesource.com/platform/packages/modules/Permission/+/26231a7eac744c7d2a8fea4740926620f56b20c6/PermissionController/res/xml/roles.xml) sets `ASSISTANT` to `requestable="false"`. Its [role documentation](https://android.googlesource.com/platform/packages/modules/Permission/+/26231a7eac744c7d2a8fea4740926620f56b20c6/PermissionController/src/com/android/permissioncontroller/role/Role.md) says a visible, non-requestable role can still be managed in Settings, but apps cannot show its request dialog. `isRoleAvailable` and `isRoleHeld` ([API](https://developer.android.com/reference/android/app/role/RoleManager)) do not prove requestability, picker availability, or button routing. PR #259 reports the exact non-requestable failure on OnePlus. **Do not guarantee a generic role chooser**, including the PR's fallback.

[`ACTION_VOICE_INPUT_SETTINGS`](https://developer.android.com/reference/android/provider/Settings#ACTION_VOICE_INPUT_SETTINGS) can have no matching activity; its API contract does not promise a uniform watch assistant picker. Resolve/check with appropriate package visibility, handle launch failure, then provide model-specific manual guidance or an explicit unavailable state. Re-read role state on returning/resuming, not just a successful activity result. A canceled/refused request must leave ordinary Herald usable.

## Cross-device setup claims

| Family | First-party evidence | Safe claim for this proposal |
| --- | --- | --- |
| Pixel Watch | Google's [assistant guide](https://support.google.com/googlepixelwatch/answer/12677020?hl=en) documents **holding the side button next to the crown**, not holding the crown. It now points to Gemini as well. | Document the OEM gesture, but the guide is about Google's assistant: it does **not** establish third-party Herald eligibility in the picker or side-button dispatch. Pixel model/OS testing remains required. Disabling “Hey Google” is not disabling Herald or changing the assistant role. |
| Galaxy Watch running Wear OS | Samsung's [assistant guide](https://www.samsung.com/us/support/answer/ANS10003405/) documents Settings → Buttons and gestures → Press and hold: Bixby/Google Assistant/power menu, explicitly excluding Alexa from that button. Its [navigation guide](https://samsung.com/us/support/answer/ANS10003406) distinguishes Home double-press, Home hold and Back short-press. Labels vary with software. | Treat the default digital assistant and Home-hold mode as separate setup steps where the firmware exposes them. Samsung documents no universal arbitrary-third-party hold mapping. A double-press app shortcut is a different affordance, not proof of hold-to-talk. |
| Older Galaxy Watch / Tizen | Samsung [identifies Watch3 and earlier as Tizen](https://developer.samsung.com/one-ui-watch-tizen/lifestyle-photo-assets/galaxy-watch3.html), and [separates Tizen and Wear OS app installation](https://samsung.com/us/support/answer/ANS10002865). | Exclude Tizen from this Android/Wear OS feature; “Galaxy Watch support” without an OS qualification is misleading. |
| OnePlus Watch 2 | #251/#259 report activity-only OEM button mapping plus role/session routing on the named firmware. | A useful reported device result, not generic Wear OS support. `AssistLaunchActivity` provides a target only where supported OEM configuration can select it; do not publish private-settings commands as normal setup. |
| Other Wear OS | Android's [physical-button API](https://developer.android.com/training/wearables/user-input/physical-buttons) lets foreground apps handle available multifunction stem keys. | This is **not** a global power/Home/assistant-button remapping API. OEM/system policy controls reserved gestures; neither an ASSIST filter nor a stem handler guarantees a hardware hold from the watch face. |

Local [Watch7 firmware research](watch7-firmware-routing.md) found an enumerated Samsung long-hold selector, not an arbitrary component launcher. Keep that exact-firmware finding separate from Samsung's public contract. **No arbitrary Samsung settings writes, shell role grants, disabling Google/Bixby, root or accessibility interception in the proposed consumer feature.**

## Optionality: recommend OS choice first; discuss capability withdrawal separately

**Recommended minimal supplement to #259:** keep the capability available, but never select Herald automatically. An “Assistant” setup/manage row explains the two routing layers, reports role state, and opens supported system settings. Installation is not opt-in to role ownership or recording. To stop using Herald as the system assistant, the user chooses another assistant (or None if offered) in the OS, and separately restores any OEM explicit button shortcut. Do not promise restoration of the previous assistant merely from changing app state. Existing tile, complication and ordinary app usage stay independent.

If maintainers want “Listen when opened as assistant,” make that a **separate** preference: off means show a usable tap-to-talk assistant, not withdraw role eligibility or leave a dead button. Apply the choice consistently to the ASSIST activity route, `AssistLaunchActivity`, and session `onShow`; decide explicitly whether existing tile/complication auto-listen remains unchanged. It is not a wake-word switch or a Gateway/Profile setting.

**Alternative: explicit capability opt-in**, e.g. “Offer Herald as a watch assistant,” initially off. A dedicated [activity alias](https://developer.android.com/guide/topics/manifest/activity-alias-element), disabled in the manifest and enabled through [`PackageManager.setComponentEnabledSetting`](https://developer.android.com/reference/android/content/pm/PackageManager#setComponentEnabledSetting(android.content.ComponentName,%20int,%20int)), can independently gate an activity-only ASSIST filter without disabling Herald's launcher/tile/complication. This is an architectural option, **not what #259 currently implements**. Move the filter off `MainActivity` if using this design; an alias alone cannot suppress that existing filter.

For #259's full stack, an alias-only switch is insufficient: the enabled `HeraldWearAssistService` can still qualify, the session remains a separate entry, and an OEM shortcut can still launch `AssistLaunchActivity`. A real capability-off transition must coordinate the qualifying service, session/recognizer dependencies, dedicated assist alias/entry and activity-only shortcut entry, while preserving ordinary app/recognizer behavior. API 33+ offers atomic [`setComponentEnabledSettings`](https://developer.android.com/reference/android/content/pm/PackageManager#setComponentEnabledSettings(java.util.List)) for dependent components; it does not atomically migrate the OS role or OEM button mapping. Enabled state is an override of manifest state; account for upgrades, restart and re-enable.

**Do not silently disable components while Herald is selected or explicitly mapped.** First guide the person to choose another assistant/None and restore the OEM shortcut; re-read role state on return. If role ownership remains or routing cannot be established safely, leave a functional non-recording entry and explain the remaining step rather than claim “Off” succeeded. Do not guess another package, write secure/global settings, or assume disabling triggers a particular fallback. Which optionality model to ship is a maintainer decision; OS-controlled selection is simpler and matches #259's current direction.

## Acceptance boundaries for an agreed follow-up spec

- Record each tested model/OS/build and distinguish: candidate visible, normal user selection, actual physical gesture, session/activity route, speech input/live voice and end-to-end Reply. No blanket “supports all Wear OS watches.”
- Cover setup cancellation, missing Settings, non-requestable role, external role changes, OEM shortcut independence and switching away; verify ordinary Herald still works when unselected/capability-off.
- Cover microphone denial, permission recovery, lock-screen privacy, cold/warm/repeated invocation, recreation, cancellation/hide, phone/Gateway absence, and no unintended recording/submission. Exercise each #259 entry path, not only `AssistEntry`'s boolean tests.
- Existing [tile](https://github.com/Giton22/herald/blob/8cc57b3e09beb1797c172d6f6a2de3af535e9915/wearApp/src/main/kotlin/dev/hermeskotlin/wear/AskTileService.kt) and [complication](https://github.com/Giton22/herald/blob/8cc57b3e09beb1797c172d6f6a2de3af535e9915/wearApp/src/main/kotlin/dev/hermeskotlin/wear/AskComplicationService.kt) are useful alternatives where available/configured. They are tap/swipe affordances, not replacements satisfying a physical hold requirement.
- Preserve Chat selection and Bot Chat continuity; this supplement does not change the Gateway protocol or override the local proposed ADRs [0001](../adr/0001-target-dashboard-protocol.md)/[0002](../adr/0002-preserve-bot-chat-continuity.md).

The user's “Complete action using / Speech recognition / Samsung Keyboard” report belongs to the **external bridge → official release** experiment described in [the earlier proposal](upstream-watch-assistant-proposal.md). The producing intent/component is unresolved. **It is not evidence of a bug in PR #259, which was not installed or tested here.** Update the final spec as a coordinated supplement to #251/#259, not a duplicate assistant-entry proposal.
